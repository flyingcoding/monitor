# v2.0-alpha：OTLP/HTTP 指标接收端点

> **状态**：v2.0-alpha 已交付 / 2026-05-18
> **范围**：服务端新增 OTLP/HTTP 指标接收端点 + 时序数据库适配层骨架。**Client 不改造**。

---

## 1. 设计目标

- **打通生态进口**：让外部 OTel Collector 把第三方采集器（Node Exporter、Telegraf、Prometheus remote_write 中转）的指标接入本项目
- **不破坏 v1.x 兼容**：Influx 写入路径、断路器降级、JSONL 缓冲与重放、Alert/SSE 链路全部保留
- **守住"轻量自托管"定位**：不引入 OTel SDK / 不上 gRPC / 不接 logs / traces

详细决策见 `.trellis/tasks/05-18-v2-0-alpha-otlp-db/prd.md`（D1–D7）。

---

## 2. 端点 API

### `POST /v1/metrics`

- **路径**：`/v1/metrics`（遵循 OTel HTTP 协议）
- **Content-Type**：`application/x-protobuf` 或 `application/json`
- **请求头**：必须包含 `X-Monitor-Token: <client-token>`
- **请求体**：标准 OTel `ExportMetricsServiceRequest`

### 响应

| HTTP 状态 | 业务码 | 场景 |
|----------|-------|------|
| 200 | success | 成功接收（即使 payload 内全是未识别 metric 也返回 200） |
| 400 | failure(400) | protobuf / JSON 解析失败 |
| 401 | unauthorized | 缺少或无效 `X-Monitor-Token` |
| 413 | failure(413) | payload 超过 `monitor.otlp.max-payload-size` |
| 503 | failure(503) | 端点被 `monitor.otlp.enabled=false` 禁用 |

响应体统一 `RestBean<Void>` 结构（与 v1.x REST API 一致）。

## 3. 鉴权与 clientId 映射（决策 D2）

- OTLP 请求 header `X-Monitor-Token` 复用客户端注册时的 token
- 服务端通过 `ClientService.findClientByToken` 解析得到目标 `Client`
- OTel resource attribute `host.name` **仅作交叉校验**：与 `client.name` 不一致时打 WARN 日志，但仍按 token 绑定的 client 写入（避免主机改名造成采集中断）

**单 token → 单 client** 是设计约定。多 client 共用一个 Collector 的场景留到 v2.0 正式版（基于 v1.2 API Token）。

---

## 4. 支持的 metric 名称（决策 D3）

服务端只接受 **`monitor.client.*` 命名空间** 下的 **Gauge 类型** 指标。其它命名空间的 metric 会被计数 + WARN 日志（不会导致 4xx）。

| OTel metric name | 单位 | RuntimeDetailVO 字段 |
|------------------|------|----------------------|
| `monitor.client.cpu_usage` | 0~1 ratio | `cpuUsage` |
| `monitor.client.memory_used_gb` | GB（已用） | `memoryUsage` |
| `monitor.client.disk_used_gb` | GB（已用） | `diskUsage` |
| `monitor.client.network_upload_kbps` | KB/s | `networkUpload` |
| `monitor.client.network_download_kbps` | KB/s | `networkDownload` |
| `monitor.client.disk_read_mbps` | MB/s | `diskRead` |
| `monitor.client.disk_write_mbps` | MB/s | `diskWrite` |
| `monitor.client.gpu_temperature_max` | ℃ | `gpuTemperatureMax` |
| `monitor.client.smart_critical_count` | 计数 | `smartCriticalCount` |
| `monitor.client.systemd_failed_count` | 计数 | `systemdFailedCount` |
| `monitor.client.watched_process_missing` | 计数 | `watchedProcessMissing` |

**为什么不直接接 `system.*` 标准名？** 客户端单位混合（ratio / GB / KB/s / MB/s），且客户端已经预算 rate，与 OTel 语义约定的 cumulative counter 不匹配。让 Collector 端做改名（`transform processor`），避免服务端引入 stateful rate 计算（决策 D3）。

## 5. OTel Collector 接入示例

下面是把 `hostmetrics` 采集到的指标中转到本系统的标准 pipeline：

```yaml
# /etc/otelcol/config.yaml
receivers:
  hostmetrics:
    collection_interval: 10s
    scrapers:
      cpu: {}
      memory: {}
      disk:
        metrics:
          system.disk.io: { enabled: true }
      network:
        metrics:
          system.network.io: { enabled: true }
      filesystem: {}

processors:
  # 关键步骤：把 system.* 改名到 monitor.client.* 并对齐单位
  transform/monitor-rename:
    metric_statements:
      - context: metric
        statements:
          # CPU utilization（OTel: 0~1 ratio）直接重命名
          - set(name, "monitor.client.cpu_usage") where name == "system.cpu.utilization"
          # Memory utilization 同样是 0~1 ratio，但我们要 GB 已用 → 这里取 used 字节按 datapoint 转 GB（示例：仅重命名，需要在 Collector 里再插一个 metricstransform 算单位）
          - set(name, "monitor.client.memory_used_gb") where name == "system.memory.usage" and attributes["state"] == "used"
          - set(name, "monitor.client.disk_used_gb") where name == "system.filesystem.usage" and attributes["state"] == "used"
          - set(name, "monitor.client.network_upload_kbps") where name == "system.network.io" and attributes["direction"] == "transmit"
          - set(name, "monitor.client.network_download_kbps") where name == "system.network.io" and attributes["direction"] == "receive"
          - set(name, "monitor.client.disk_read_mbps") where name == "system.disk.io" and attributes["direction"] == "read"
          - set(name, "monitor.client.disk_write_mbps") where name == "system.disk.io" and attributes["direction"] == "write"

  # 必填：在 resource 上加 host.name 以便 server 端交叉校验
  resourcedetection:
    detectors: [system]
    system:
      hostname_sources: [os]

exporters:
  otlphttp/monitor:
    endpoint: http://monitor-server:8001
    # 关键：通过 headers 传 X-Monitor-Token
    headers:
      X-Monitor-Token: "<your-client-token-here>"
    # 仅启用 metrics path
    metrics_endpoint: http://monitor-server:8001/v1/metrics

service:
  pipelines:
    metrics:
      receivers: [hostmetrics]
      processors: [resourcedetection, transform/monitor-rename]
      exporters: [otlphttp/monitor]
```

> **注**：上面 `system.memory.usage` / `system.filesystem.usage` 的单位是字节，而 `monitor.client.memory_used_gb` 期待 GB。需要在 transform processor 后再插一个 `metricstransform` 或 `filter/group_by_attrs + math expression` 把字节除以 `1073741824`。完整的单位转换流水线视部署而定，本文不固化具体写法。

## 6. curl 端到端验证

### Protobuf

需要先用 `protoc` 把 OTel 协议生成 Java/Python/Go bindings 构造消息，对纯 curl 调试不友好。建议测试用 JSON 形式。

### JSON

```bash
curl -sS -X POST http://localhost:8001/v1/metrics \
  -H 'X-Monitor-Token: token-aaa-bbb-ccc' \
  -H 'Content-Type: application/json' \
  -d '{
    "resourceMetrics": [
      {
        "resource": {
          "attributes": [
            {"key": "host.name", "value": {"stringValue": "host-01"}}
          ]
        },
        "scopeMetrics": [
          {
            "metrics": [
              {
                "name": "monitor.client.cpu_usage",
                "gauge": {
                  "dataPoints": [
                    {
                      "timeUnixNano": "1700000000000000000",
                      "asDouble": 0.42
                    }
                  ]
                }
              }
            ]
          }
        ]
      }
    ]
  }'
# {"code":200,"message":"请求成功","data":null,"reqId":"..."}
```

写入后前端 `客户端管理 → 详情` 即可看到 CPU 曲线更新。

## 7. 配置项

| 配置 | 默认 | 环境变量 | 说明 |
|------|------|---------|------|
| `monitor.otlp.enabled` | `true` | `MONITOR_OTLP_ENABLED` | 是否启用 OTLP 端点。`false` 时所有请求 503 |
| `monitor.otlp.max-payload-size` | `4194304` (4 MiB) | `MONITOR_OTLP_MAX_PAYLOAD_SIZE` | 单次请求 payload 上限字节 |
| `monitor.tsdb.provider` | `influxdb` | `MONITOR_TSDB_PROVIDER` | 时序后端：`influxdb` 默认 / `victoria-metrics` v2.0-alpha 占位（自动回落到 influxdb） |

## 8. 时序数据库适配层

v2.0-alpha 抽出 `com.example.tsdb.TimeSeriesAdapter` 接口，把 `InfluxDbUtils` 中的全部写入/查询逻辑迁入 `InfluxDbProvider`，并为 v2.0-beta 的 `VictoriaMetricsProvider` 预留接口。

```
com.example.tsdb/
├── TimeSeriesAdapter           # 接口：writeRuntime / writeOtlpMetric / readRuntimeHistory / readAvailabilityBuckets
├── InfluxDbProvider            # 默认实现，收编断路器 + JSONL 缓冲降级 + 重放
├── VictoriaMetricsProvider     # 占位 stub，所有方法抛 UnsupportedOperationException
└── TsdbAdapterFactory          # 按 monitor.tsdb.provider 装配，victoria-metrics WARN 回落
```

- Resilience4j circuit-breaker 名仍为 `influxdb`（与 v1.x yml 配置一致，不改动）
- v2.0-beta 实装 VM 时再统一改 `tsdb` 或保留 per-provider 多实例

## 9. 已知限制（v2.0-alpha）

- **不支持 OTLP gRPC**：仅 HTTP/Protobuf + HTTP/JSON
- **不支持 cumulative counter 自动 rate**：Collector 端用 `deltatorate` 或 `metricstransform` 自行计算
- **VictoriaMetrics Provider 未实装**：配 `monitor.tsdb.provider=victoria-metrics` 会 WARN 后回落到 InfluxDb，**不是 fail-fast**（决策 D7）
- **不支持 OTLP Logs / Traces**：路线图明确不做
- **单 token 单 client**：跨主机共用 Collector 暂不支持
- **前端无单独 OTLP 来源标识**：OTLP 写入与 client 直传合流到同一 `runtime` measurement，UI 不区分来源
