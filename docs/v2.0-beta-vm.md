## 1. 总览

v2.0-beta 让 `com.example.tsdb.VictoriaMetricsProvider` 从 v2.0-alpha 的占位 stub 进化为完整可用的时序后端实现。
用户切换 `monitor.tsdb.provider=victoria-metrics` 后，所有 v1.x / v2.0-alpha 行为（写入、查询、断路器降级、JSONL
缓冲与重放、SSE 实时推送、告警引擎、状态页可用率）零回归。

### 1.1 核心决策（D1-D7，详见 `.trellis/tasks/05-19-v2-0-beta-victoriametrics-provider-vmctl/prd.md`）

| ID | 决策 |
|----|------|
| D1 | MVP 范围 = Approach B（完整生产可用）：4 方法全实现 + 断路器名修正 + docker-compose 双 profile + 完整迁移文档 |
| D2 | 断路器名 `influxdb` → `tsdb`；yml namespace 重构为 `monitor.tsdb.{influxdb,victoria-metrics,buffer}.*`；deprecated alias 保留 1 个 minor 版本 |
| D3 | metric 命名天然统一（vmctl 历史 + VM provider + OTLP 都映射到 `runtime_<field>`），无 union 复杂度 |
| D4 | JSONL 缓冲单目录共享（`data/influx-buffer/` → `data/tsdb-buffer/`），跨 provider 重放业务 VO |
| D5 | OTLP 写入不加 source label，保持 OTLP/直传合流 |
| D6 | docker-compose 中 VM（`profile=vm`）+ vmctl（`profile=migration`）都 opt-in，`make up` 默认行为不变 |
| D7 | WireMock 主力单测 + Testcontainers VM v1.143.0 可选集成测试 |

## 2. 部署：启用 VictoriaMetrics

VM 是 **opt-in 升级路径**而非默认平替。`make up` 默认仍只起 InfluxDB；VM 单独通过 profile 启用。

### 2.1 启动 VM 容器

```bash
# 启动 VM（profile=vm，单节点 victoria-metrics:v1.143.0）
make up-vm

# 等价命令
docker compose --profile vm up -d victoria-metrics

# 验证健康
curl http://localhost:8428/health
# 期望：OK
```

### 2.2 切换 server 写入路径

在 `.env` 设置：

```bash
MONITOR_TSDB_PROVIDER=victoria-metrics
VM_URL=http://victoria-metrics:8428
```

然后重启 server：

```bash
docker compose restart monitor-server
```

启动日志应看到：

```
INFO  com.example.tsdb.TsdbAdapterFactory -- monitor.tsdb.provider=victoria-metrics → 注入 VictoriaMetricsProvider 作为主时序后端
INFO  com.example.tsdb.VictoriaMetricsProvider -- VictoriaMetricsProvider 已初始化，写入端点=http://victoria-metrics:8428/api/v2/write，查询端点=http://victoria-metrics:8428/api/v1/query_range（超时 5000ms）
```

### 2.3 回滚到 InfluxDB

```bash
# 改回 .env
MONITOR_TSDB_PROVIDER=influxdb
docker compose restart monitor-server
```

InfluxDB 容器持续运行（默认拓扑），数据未受影响。

## 3. vmctl 迁移：InfluxDB 2.7 → VictoriaMetrics

历史数据迁移是 v2.0-beta 配套交付物。本节给出完整步骤。

### 3.1 关键限制（必读）

> **vmctl 不直接支持 InfluxDB v2 API**（[VictoriaMetrics#5914](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/5914)，open since 2024-03）。
> 本项目用 InfluxDB 2.7，必须走 **v1 兼容 workaround**——先在 InfluxDB 上创建 v1 凭证 + DBRP 映射，
> 让 vmctl 把 InfluxDB 2.7 当作 v1 来读。

### 3.2 步骤 1：在 InfluxDB 2.7 上创建 v1 凭证

进入 InfluxDB 容器：

```bash
docker exec -it monitor-influxdb bash
```

获取 bucket ID：

```bash
influx bucket list -t <admin-token> | grep program
# 输出形如：a1b2c3d4e5f6  program  ...
```

创建 v1 兼容凭证（密码自定义）：

```bash
influx v1 auth create \
  --username monitor-v1 \
  --password "vmctl-readonly-2026" \
  --read-bucket <bucket-id-from-above>
```

创建 DBRP 映射（让 v1 客户端通过 database 名 `program` 找到 bucket）：

```bash
influx v1 dbrp create \
  --bucket-id <bucket-id-from-above> \
  --db program \
  --rp autogen \
  --default
```

退出容器：

```bash
exit
```

### 3.3 步骤 2：填写 .env 中的 v1 凭证

```bash
INFLUX_V1_USERNAME=monitor-v1
INFLUX_V1_PASSWORD=vmctl-readonly-2026
INFLUX_V1_URL=http://influxdb:8086
```

### 3.4 步骤 3：运行 vmctl

确保 VM 已启动（`make up-vm`），然后：

```bash
make migrate-influx-to-vm

# 等价命令
docker compose --profile migration run --rm vmctl-migrate
```

vmctl 输出示例：

```
InfluxDB import mode
2026/05/19 16:30:00  Found 1 databases to import.
2026/05/19 16:30:00  Database "program" import started
2026/05/19 16:30:05  ...
2026/05/19 16:30:42  Total: 285M samples; took 42s
```

### 3.5 步骤 4：验证迁移结果

```bash
# VM 内查 series 数
curl 'http://localhost:8428/api/v1/series?match[]={__name__=~"runtime_.*"}' | jq 'length'
# 期望：11 × N（N = 你的客户端数量）

# 查最近 1h 的 cpuUsage
curl 'http://localhost:8428/api/v1/query?query=runtime_cpuUsage{clientId="1"}' | jq
```

前端"客户端详情 → 历史曲线"页面应能渲染历史数据。

### 3.6 故障排查

| 症状 | 原因 | 解决方案 |
|------|------|---------|
| vmctl 抛 `401 Unauthorized` | v1 凭证错误或 DBRP 没建 | 复核 §3.2 步骤；确认 `influx v1 auth list` 能看到凭证 |
| `Found 0 databases to import` | DBRP 映射缺失 | 重跑 `influx v1 dbrp create` |
| 数据量远小于预期 | 迁移命令 `--influx-database` 与实际 DBRP `--db` 不一致 | 改 `.env` 中 `INFLUX_BUCKET`（vmctl 用它作为 db 名） |
| vmctl 中途网络异常 | 暂时性 | 重跑 `make migrate-influx-to-vm` —— vmctl 对 (series, ts) 写入幂等 |
| 想中断 vmctl | 长时任务 | `Ctrl+C` 或 `docker stop monitor-vmctl-migrate`；下次重跑即可 |

## 4. 架构变更细节

### 4.1 yml 配置 namespace 重构（D2）

| 旧 key（v1.x / v2.0-alpha） | 新 key（v2.0-beta） | 兼容期 |
|----------------------------|--------------------|--------|
| `spring.influx.url` | `monitor.tsdb.influxdb.url` | 至 v2.1.x 移除 |
| `spring.influx.user` | `monitor.tsdb.influxdb.user` | 至 v2.1.x 移除 |
| `spring.influx.password` | `monitor.tsdb.influxdb.password` | 至 v2.1.x 移除 |
| `spring.influx.bucket` | `monitor.tsdb.influxdb.bucket` | 至 v2.1.x 移除 |
| `spring.influx.organization` | `monitor.tsdb.influxdb.organization` | 至 v2.1.x 移除 |
| `monitor.influx-buffer.dir` | `monitor.tsdb.buffer.dir` | 至 v2.1.x 移除 |
| `monitor.influx-buffer.replay-interval-ms` | `monitor.tsdb.buffer.replay-interval-ms` | 至 v2.1.x 移除 |
| `monitor.influx-buffer.batch-size` | `monitor.tsdb.buffer.batch-size` | 至 v2.1.x 移除 |

启动时 `TsdbAdapterFactory` 检测到旧 key 显式定义会打 WARN，提示用户迁移到新 namespace。
旧 key 仍可读（通过嵌套占位符 `${new:${old:}}`），不会破坏现有部署。

### 4.2 断路器名重构（D2）

`resilience4j.circuitbreaker.instances.influxdb` → `tsdb`。同一份配置驱动 InfluxDB 与 VM 两个 provider 的
fallback 节奏。yml 完整片段：

```yaml
resilience4j:
  circuitbreaker:
    instances:
      tsdb:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 10
        minimum-number-of-calls: 5
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3
        automatic-transition-from-open-to-half-open-enabled: true
```

### 4.3 JSONL 缓冲目录共享（D4）

| 路径 | 用途 |
|------|------|
| `data/tsdb-buffer/*.jsonl` | 任一活跃 provider 写入失败时的降级缓冲 |
| `data/tsdb-buffer/archive/*.jsonl` | 重放成功后的归档 |
| `data/influx-buffer/` | v1.x / v2.0-alpha 旧目录；启动时若存在且新目录为空，自动迁移 JSONL 到新目录 |

切换 provider 时旧目录里"未传到 InfluxDb 的数据"会被新 provider 自动重放——这是 feature 不是 bug。

### 4.4 VictoriaMetrics 实现细节

| 接口方法 | 实现策略 |
|---------|---------|
| `writeRuntime` / `writeOtlpMetric` | 复用 `influxdb-client-java`（VM 兼容 `/api/v2/write`），与 InfluxDbProvider 走相同 `BeanUtils.copyProperties` 路径 |
| `readRuntimeHistory` | Spring `RestClient` 调 `POST /api/v1/query_range`，PromQL: `{__name__=~"runtime_.*", clientId="<id>"}`，step=10s |
| `readAvailabilityBuckets` | MetricsQL: `present_over_time(runtime_cpuUsage{clientId="<id>"}[30m])`，step=30m，48 桶右对齐 |
| 断路器 fallback | 失败时调 `InfluxDbProvider.writeRuntime`（其自身又走 `@CircuitBreaker(name="tsdb")`），形成 "VM → Influx → JSONL" 级联降级 |

## 6. 限制与已知问题

- **不支持 VM 集群模式**（vminsert/vmselect/vmstorage 多节点）；v3.0+ 评估
- **不支持双写过渡桥**（Approach C，D1 explicitly out-of-scope）
- **vmctl 无 InfluxDB v2 原生支持**（已通过 §3 workaround 缓解；upstream issue 跟踪 [#5914](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/5914)）
- **写入路径无 Spring AOP 时断路器不生效**：单元测试中通过反射调用 fallback 验证语义；端到端断路器行为依赖 PR5 集成测试
- **`query-timeout-ms` 仅控制 HTTP 超时**：PromQL 查询本身的 server-side timeout 由 VM `-search.maxQueryDuration` 决定（默认 30s，未在本期暴露 yml）

## 7. 升级路径

### 7.1 从 v1.x / v2.0-alpha 升级到 v2.0-beta

1. `git pull` 拉到 v2.0-beta tag
2. `make build` 构建新的 server / web 镜像
3. `docker compose up -d --build`（默认拓扑保持 InfluxDB；现有数据零迁移）
4. （可选）按 §2 / §3 启用 VM：
   - `make up-vm` 启动 VM 容器
   - 用 §3 步骤运行 vmctl 迁移历史数据（可选）
   - 改 `.env` 中 `MONITOR_TSDB_PROVIDER=victoria-metrics`
   - `docker compose restart monitor-server`
5. yml 兼容兜底：原 `spring.influx.*` / `monitor.influx-buffer.*` 仍可读，但启动 WARN 提示迁移到 `monitor.tsdb.*` namespace；v2.1.x 计划移除

### 7.2 从 v2.0-beta 回滚到 v1.x

1. `git checkout <v1.x-tag>`
2. `make build && docker compose up -d --build`
3. 若已 vmctl 迁移过历史数据到 VM，VM 容器不影响 v1.x 行为（v1.x 不读 VM）；可 `make down-vm` 停掉
4. `data/tsdb-buffer/` 中的缓冲会被 v1.x 当作 `data/influx-buffer/` 处理（命名不一致需手工 rename）
